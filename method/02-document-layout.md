# ドキュメント構成 — シナリオSDD の運用層

この文書は憲法（`00-constitution.md`）を運用に落とすための規約であり、
個別シナリオ・プロジェクト（本テンプレートから分岐した先）が従うフォルダ構成を定める。

> この文書を含む `method/` 配下（手法そのもの）はステータス接尾辞を持たない。
> ステータスは「対象をどれだけ信じてよいか」を示すものであり、手法自身は常に信頼される前提に置くため（第3-2節参照）。

---

## 1. 4層モデル

憲法の「背景と生成物を分ける」を、4つの層として物理ツリーに写す。
左ほど Locked 寄り、右へ行くほど Open 寄り。

| 層 | フォルダ | 役割 | 凍結 |
|---|---|---|---|
| **仕様層** | `spec/` | 設計・拘束。物語の骨格を定義する | Locked 寄り |
| **計画層** | `plans/` | 生成単位ごとの「生成前計画書」 | 合意で Locked → 生成へ |
| **生成物層** | `output/` | 本文のみ。連結すれば通し読みできる | Open（計画の範囲内で可変） |
| **背景層** | `decisions/` | なぜそう決めたか・却下案・方針転換 | 追記型（消さない） |

---

## 2. ディレクトリ構成

```
<シナリオ>/
├── spec/                      # 仕様層（設計・拘束）
│   ├── 00-anchor.<status>.md      # アンカー（型・正副・抽象面/具体面・Locked/Open）
│   ├── 10-opposition.<status>.md  # 骨1: 対立軸
│   ├── 20-origin.<status>.md      # 骨2: 主人公の初期状態（逆算）
│   ├── 30-spine.<status>.md       # 骨3: 因果の背骨（ビート列）
│   ├── 40-cast/                   # 肉4: 配役（1キャラ＝1フォルダ）
│   │   └── NN-<character>/         # 人物構築プロトコル（04-character-protocol）
│   │       ├── 00-core.<status>.md      # 核＋原型反応＋欲求と恐れ＋禁則
│   │       ├── 10-voice.<status>.md     # 声と知覚
│   │       ├── 20-relations.<status>.md # 座組内の差分
│   │       └── 30-arc.<status>.md       # spine 沿いの変化
│   └── 50-world/                  # 肉5: 世界・設定（必要駆動）
│       └── NN-<topic>.<status>.md
├── plans/                     # 計画層（生成前計画書）
│   └── NN-<unit>.<status>.md
├── output/                    # 生成物層（本文のみ）
│   └── NN-<unit>.<status>.md
└── decisions/                 # 背景層（決定ログ・追記型）
    └── NNNN-<topic>.md
```

## 3. 命名規則

### 3-1. 項番プレフィックス

- **全ディレクトリのファイルに項番プレフィックス**を付け、任意の分かりやすい順にソートできるようにする（アルファベット順に縛られない）。
- 番号は **10 刻み**で採番し、間に挿入余地を残す（`10, 20, 30…`）。
- `spec/` 直下の構造ファイル（`00〜50`）は**構築順＝骨→肉のセオリー順**で固定。

### 3-2. ステータス接尾辞

**ステータスは「その対象をどれだけ信じてよいか（信頼度）」を示す。**
`.draft` は暫定で鵜呑みにしてはならず、`.locked` は信頼してよい確定物である。

- ステータスを持つファイルは、**ファイル名の接尾辞でステータスを表す**（ツリーを見ただけで信頼度が分かる）。
- 値は2つ：
  - `.draft` … Open（未承認／暫定／提案。まだ信じきってはいけない）
  - `.locked` … Locked（承認済み／信頼してよい確定物）
- 承認時に `.draft` → `.locked` へ**リネーム**する。変更履歴は Git が保持する。
- `decisions/` は追記型の記録なのでステータスを持たない（`NNNN-<topic>.md`）。

**ステータスを持たないもの＝常に信頼される前提のもの。**
`method/` 配下（手法そのもの）はここに当たる。システム自身が暫定だと、その上の判断がすべて揺らぐため、手法は常に信頼される確定物として扱い、接尾辞を付けない。

### 3-3. 語幹（安定キー）

- 参照は**ステータス接尾辞を含まない「語幹」**で行う。
  - spec：`spec/00-anchor`、`spec/30-spine`
  - 人物（フォルダ）：`spec/40-cast/10-charlotte`。サブ要素は `#` で指す（`…#core`、`…#voice`、`…#arc-beat-7`）。
  - 生成単位：`<NN>-<unit>`（例 `30-ten`）。`plans/` と `output/` で同じ語幹を共有する。
- 語幹に一致する実体ファイルは各フォルダに**唯一**とする。
- これにより、承認でステータス接尾辞が変わっても参照は壊れない（トレーサビリティ／憲法第4条を守る）。

---

## 4. 2種類の番号付け（憲法第1条の可視化）

番号系統は意図的に2つある。

- `spec/` 直下の `00/10/20/30/40/50` = **構築順**（骨→肉のセオリー順）。上から読むと憲法第3条の手順になる。
- `plans/` `output/` の `<NN>` = **物語順**（起承転結の読む順）。連結すると本文を通し読みできる。

**構築順 ≠ 物語順**を別軸として持てる。物語順 `30-ten` を最初に構築してよい、という第1条の非線形性がここに表れる。

---

## 5. トレーサビリティの実装（憲法第4条）

`plans/` と `output/` の各ファイル冒頭に front-matter を必須化し、根拠を機械可読にする。

**`output/30-ten.draft.md` の例：**
```markdown
---
unit: 30-ten                   # 語幹（安定キー）
derives_from:                  # どの仕様・計画を実現するか（語幹で参照）
  - spec/00-anchor#primary
  - spec/30-spine#beat-7
  - plans/30-ten
---

（ここに本文）
```

- ステータスは front-matter に持たない（ファイル名が真実の源）。
- `derives_from` は語幹参照。実体はステータスに依らず解決される。

**`plans/NN-<unit>` に書くこと：**
- この単位で**達成すべきこと**（アンカーの抽象面〈Message／核〉のどの面に奉仕するか）
- 仕様からの**制約**（Locked 事項の再掲）
- この単位内での **Locked / Open の線引き**
- **受け入れ基準**（＝抽象面を満たすかの判定条件。審査対象）

計画が `.locked` になって初めて `output/` の生成に進む。ここが検問所（憲法第5条）。

---

## 6. 「修正」の流れ（フォルダで版を積まない）

- 本文がどう変わったか → **Git のコミット履歴**。`*.v2.md` のような版ファイルは作らない。
- *なぜ*変えたか（方針転換・却下） → **`decisions/` に追記**。
- 修正が仕様に波及したら → 該当 `spec/` を更新し、**審査プロトコルの「矛盾掃引」で他ページの同一事項も直す**。

`decisions/NNNN-<topic>.md` は ADR 形式：**決定 / 背景 / 却下した代替案 / 影響する仕様（語幹参照）**。追記型で過去エントリは消さない。

---

## 7. 効いてくる性質

**`output/` を番号順に連結 ＝ 完成シナリオの通し読み。**
生成物層に本文以外を混ぜないから成立する。これが「背景と生成物を分ける」の実利であり、
AI に対しても「`output/` だけが本文、他はすべて背景」と一言で渡せる。
