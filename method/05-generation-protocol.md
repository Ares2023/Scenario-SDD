# 生成プロトコル — AI への引き渡し規約

この文書は、確定した仕様・計画を **AI に渡して `output/` の本文を生成／改稿させる**手順を定める。
憲法第5条（人間の承認をもって Locked）と構成規約 第5節（plans が `.locked` になって初めて生成）を、
**実際の引き渡し**に落としたもの。

> 本手法の目的は「**AI に予期しない編集をさせず、背景と生成物を分けて正確に生成させる**」こと（README）。
> その目的を実装するのがこの文書。ここが無いと、上流の仕様は「消費者のいない仕様」に終わる。

---

## 1. 前提：生成に入る条件

- 生成に入ってよいのは、その単位の `plans/NN-<unit>` が **`.locked`** のときだけ（検問所＝憲法第5条）。
- `.draft` の計画からは生成しない。まず審査（`01-review-protocol`）を通す。

---

## 2. 文脈パッケージ（AI に渡すもの／渡さないもの）

生成単位ごとに、AI に渡す文脈を**明示的に組み立てる**。渡しすぎ・渡さなすぎの両方が事故を生む。

### 渡す（優先度つき）

1. **当該 `plans/NN-<unit>`（.locked）** — 何を達成するか・Locked/Open の線引き・受け入れ基準。最優先。
2. **plans が `derives_from` で指す spec**（語幹で解決）：
   - `spec/00-anchor` の**抽象面**（Message／核）— ものさし
   - `spec/30-spine` の**該当 beat**
   - 登場する人物の `spec/40-cast/<char>#core` と `#voice`
   - その単位が要求する `spec/50-world` のトピックのみ
3. **`spec/60-form`（様式仕様）** — 視点・時制・文体・媒体。表層のものさし。
4. **直前・直後の `output`**（連続性が要るとき）。

### 渡さない

- 無関係な spec・他単位の plans（文脈汚染）。
- **`decisions/`**（背景は生成に混ぜない。なぜ決めたかは生成に不要）。
- **`ideas/`**（採否未定。**絶対に本文へ引き込まない**。構成規約 第7節）。

原則：**Locked は「守る文脈」、Open は「埋めてよい余白」として区別して渡す。**

---

## 3. 生成契約（AI が守る規則）

渡すときに、次を契約として明示する。

- **`plans` の Open 範囲だけを書く。** Locked 事項は動かさない・言い換えない・要約し直さない。
- **spec に無い世界設定・人物事実を捏造しない。** 必要になったら生成を止め、上流へ質問する（第4節）。
- **声は該当人物の `#voice` に従う。** 台詞を他キャラに差し替えても成立する書き方をしない（審査 2-7）。
- **様式は `spec/60-form` に従う。** 視点・時制・文体を単位内で揺らさない。
- **出力は本文のみ。** 冒頭 front-matter（`unit` / `derives_from`）を付け、それ以外の解説・メモを本文へ混ぜない（構成規約 第8節：output は連結で通し読みできる状態を保つ）。

---

## 4. 逸脱申告（下流 → 上流への還元／憲法第4条）

生成は「本文」だけでなく、**気づきの申告**も返す。これを本文とは**別枠**で受け取る。

AI が申告すべきもの：

- Locked と矛盾して**書けなかった**点。
- spec の**穴**：未定義の設定、beat 間の飛躍（機構不成立＝審査 2-1）、人物の禁則との衝突（審査 2-8）。
- 使えそうな**未使用の伏線**（審査 2-4）。

人間はこの申告を、**本文に混ぜず**に振り分ける：
- 仕様の修正が要る → `spec/`／`plans/` を直し、再審査（矛盾掃引 2-6 を波及先へ）。
- 決定として残す → `decisions/`。
- 今は保留 → `ideas/`。

---

## 5. 改稿の規律（版を積まない）

- **Locked を触らない改稿**は、Open 範囲を指定して頼む（「この段落の描写だけ」）。版ファイル（`*.v2`）は作らない。変更は Git 履歴、理由は `decisions/`（構成規約 第6節）。
- **Locked を変える必要が出たら、その場で本文を書き換えさせない。** いったん生成を止め、`spec/`／`plans/` に戻って審査 → 再 `.locked` → 再生成。
  - 理由：Locked は信頼度の基盤。本文都合で上流を黙って書き換えると、トレーサビリティ（憲法第4条）が崩れる。

---

## 6. 完成判定（output の draft → locked）

- `output/NN-<unit>.draft` を、その単位の `plans` の**受け入れ基準**（＝審査項目の具体化。`01-review-protocol` 第4節）で裁く。
- 人間が承認したら `.draft` → `.locked` にリネーム。
- 承認が上位仕様に波及するなら、矛盾掃引（審査 2-6）を仕様全体へ回してから確定する。

---

## 7. 引き渡し文の雛形（コピーして使う）

実際に AI へ渡すときの定型。`〈〉` を埋める。

```
あなたは 〈作品名〉 の本文生成を担当する。仕様駆動で書く。

【本文はどれか】
- output/ だけが本文。他（spec/plans/decisions/ideas）はすべて背景。

【今回の単位】
- plans/〈NN-unit〉（.locked）を実現する本文を書く。

【守る文脈（Locked：動かすな・言い換えるな）】
- 〈spec/00-anchor の抽象面〉
- 〈spec/30-spine#beat-N〉
- 〈登場人物の #core / #voice〉
- 〈spec/60-form：視点・時制・文体・媒体〉

【埋めてよい余白（Open）】
- 〈plans の Open 事項〉

【禁止】
- Locked の改変・言い換え／spec に無い設定・人物事実の捏造／本文以外の混入。

【出力】
1. 本文（冒頭に front-matter: unit, derives_from）。
2. 別枠で「逸脱申告」：書けなかった点・spec の穴・使えそうな未使用要素。
   ※申告は本文に混ぜない。
```

この雛形を単位ごとに埋めて渡す。返ってきた逸脱申告は第4節の経路で処理する。
