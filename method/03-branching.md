# ブランチ戦略 — テンプレートと実シナリオの分離

この文書は、手法・テンプレート（本リポジトリ）と、そこから育てる個別シナリオを
Git のブランチでどう分離・同期するかを定める。

---

## 1. モデル

- **`main`** … 手法とテンプレートそのもの（`method/` + `templates/`）。実シナリオの本文は置かない。
- **`scenario/<作品名>`** … 個別シナリオ。`main` から分岐する。

別リポジトリには分けない。1リポジトリ内をブランチで分ける。

---

## 2. 新シナリオの開始手順

```bash
git switch main
git switch -c scenario/<作品名>          # 例: scenario/charlotte
cp -r templates/scenario/* .            # ルートへ「コピー」（移動しない：第4節参照）
# フォーム(_*.template.md)は使うときにコピーするので、不要なら削除してよい
git add -A
git commit -m "chore: <作品名> をテンプレートから開始"
```

展開後のシナリオブランチの姿：

```
<repo>/
├── method/        # 手法（読み取り専用。ここでは編集しない）
├── templates/     # 種（残す。無視してよい。第4節参照）
├── spec/          # ← ここから下が実シナリオ本体
├── plans/
├── output/
└── decisions/
```

`output/` をルートに置くことで「番号順に連結＝通し読み」が成立する（憲法・構成規約 第7節）。

---

## 3. 記入とステータス

- ルートの `spec/` から憲法第3条の順（骨→肉）で埋める。
- 承認された要素は `.draft` → `.locked` にリネーム（審査プロトコル）。
- **`method/` はこのブランチで編集しない**（第5節）。

---

## 4. テンプレ・手法の更新反映（一方向：main → scenario）

手法や雛形の改善は **必ず `main` で行う**。各シナリオへは次で取り込む：

```bash
git switch scenario/<作品名>
git merge main
```

- `method/` は両ブランチで同一パスなので**クリーンに更新が流れる**（シナリオは常に最新の手法に従える）。
- `templates/` の更新は**ルートの本文に触れない**（パスが違うため）。改善された雛形を使いたければ、その差分だけ手で取り込む。
- **マージは一方向。`scenario → main` は行わない**（本文を `main` に混ぜない）。

### なぜ「コピー」で「移動」しないか
ブランチ作成時に `templates/scenario/` を移動（削除）すると、後で `git merge main` した際に
「`main` では更新／ブランチでは削除」の **modify/delete 衝突**が起きる。
コピーして `templates/` を残せば衝突しない。**だからシナリオブランチでも `templates/` は削除せず残す**（中身は無視してよい）。

---

## 5. 手法の穴に気づいたら

シナリオ制作中に `method/` の不備を見つけても、**その場（scenario ブランチ）で直さない。**
`main` で修正し、`git merge main` で降ろす。

理由：ステータス＝信頼度であり、`method/` は「常に信頼される確定物」（構成規約 第3-2節）。
個別シナリオの都合で手法を書き換えると、他の全シナリオがよって立つ基盤が枝ごとに食い違い、信頼が崩れる。

---

## 6. 運用上の注意

- ブランチ名は **romaji のスラッグ**を推奨（例 `scenario/charlotte`）。ツール互換のため。
- 各シナリオブランチは**互いに独立**。合流させない。
- 画像等のバイナリ資産は `output/` に置かない（通し読み性とリポジトリ肥大の回避）。必要なら別管理か Git LFS。
